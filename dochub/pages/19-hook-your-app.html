The dumb version (read this first)

  1. You have a website. Attackers hit it. The website writes a log line every time.
  2. A tiny program on that box (the agent) reads new log lines and mails them to the monitor. It does not sit in front of the site. It does not block anyone.
  3. The monitor is a different box. It looks at the lines. If a line looks like an attack, it shows up on the map.
  4. Some attacks never appear in the log (a failed password in a POST body, “user A read user B’s invoice”). For those, the website itself sends one tiny JSON postcard to the monitor. Only when something bad happened. Not for every page view.
You do not need a new product There is no extra webhook SaaS. There is no UDP magic. There is no Java agent. The postcard is POST /api/ingest with the same token the agent already uses.

The manager throws away boring successes: a 200 for style.css or /assets/logo.png is not stored and not mapped. A 404 on that same file still counts. A 200 on /assets/../.env still counts.

Two planes (why the site stays fast)

Edge planeApp plane
Who The agent, reading nginx / Caddy access logs Your application code
When Every new log line (the process sleeps until there is one) Only when a security line is crossed
Good for Internet noise: scanners, /.env, 404 storms, SQLi in the URL Things the log cannot see: failed login, canary, IDOR, bad webhook
Volume Can be chatty. Cheap. Happens on the web box, parse happens on the monitor. Rare. Rich. Never wait for the monitor to answer.

ACMECo keeps both. They do not rip the agent out of fear. They do not send every successful API call from Node.

There is no special ACMECo API and no signed webhook from us to you. You call us. We do not call you.

Plane 1 — put the agent on the web box

gpewebdefender agent \
  --url http://MONITOR:8787 \
  --token SECRET \
  --name acme-web-1 \
  --tail /var/log/nginx/access.log

--name is the label in the Hosts dropdown. Use a word, not the public IP. Add --journal if you also want SSH / sudo on that Linux box.

The agent starts at the end of the file. It does not re-read history. It batches lines and POSTs them. Then it sleeps. It is not a Java indexer.

Plane 2 — the app sends a postcard (only when it matters)

ACMECo’s login handler already knows the password was wrong. The access log does not. So after they return 401 to the browser, they fire this and do not wait for our reply: 

POST /api/ingest
Authorization: Bearer SECRET
Content-Type: application/json
X-SIEM-Source: acme-api

{ "kind": "applogin", "src_ip": "203.0.113.9", "user": "alice",
  "path": "/login", "status": 401, "outcome": "fail" }

When ACMECo’s own code catches a security miss (not a normal page view):

{ "kind": "secprobe", "src_ip": "203.0.113.9",
  "reason": "idor", "path": "/invoices/999", "status": 403, "user": "alice" }
kindWhen ACMECo sends it
apploginStaff / user login fail (or ok, if they want a ratio)
tenantloginA site-owner login, if they have that idea
secprobeCanary, probe, IDOR, webhook, 2FA skip, … (see reasons)
Never put these in the JSON Passwords. Session cookies. API keys. Webhook signatures. Card numbers. File contents. The monitor does not need them and you do not want them on disk.

In Node / Go / anything: start the POST and return your 401/403 to the user immediately. If the monitor is down, drop the postcard. The website still works.

The reason list (copy-paste for the app team)

Send exactly these strings. The monitor already has a rule for each.

reasonPlain English
canary_hitSomeone requested the decoy URL
path_probeURL had ../, .env, admin junk
sensitive_deny401/403 on a privileged route
webhook_rejectBad webhook signature
auth_rate_limitToo many logins, you sent 429
enum_burstOne IP guessed lots of public IDs
app_denyA feature said no without credentials
idorAlice tried to open Bob’s invoice
priv_escAlice tried to become admin
key_replayA stolen or reused key
ssrf_outYou blocked a fetch to a private IP
upload_abuseHostile upload
ws_abuseSocket / live channel abuse
logic_denyNegative price, qty cheat, etc.
stepup_bypassTried to skip 2FA

If ACMECo cannot detect IDOR yet, they do not send idor. The monitor cannot invent it from nginx. Fix the app, then POST.

Plant a canary (five minutes)

  1. Make this URL exist and return 404 or 403: /.well-known/siem-canary (or /__canary__/siem).
  2. Do not link it from the real UI. You may list it in robots.txt as Disallow — scanners read that file on purpose.
  3. Either the access-log agent will see the GET (plane 1), or the app POSTs reason=canary_hit (plane 2). Both is fine.
  4. One hit is enough. If a real customer can click it, you planted it wrong.

Do not

  • Wait for the monitor before answering the user
  • POST every 200 OK from the app
  • Replace the agent with “only async.” Then you miss /.env probes that never reach the app
  • Send logs with UDP only and delete the disk file — drops lose evidence
  • Put a heavy Java agent on the same box that serves customers
  • Write ACMECo’s real hostnames or tokens into this repo

Checklist (ACMECo ships Friday)

  1. Monitor up. Token in the env file. Firewall: ingest only from the web box.
  2. Agent on the web box. Name acme-web-1. First scanner should appear under Hosts.
  3. Open the UI. Live → Web if login noise is loud. Reports → vectors / auth / probes.
  4. App: fire-and-forget POST for login fails. Confirm Reports → Auth · App.
  5. Plant /.well-known/siem-canary. Hit it once from a laptop. Confirm a canary alert.
  6. When the app can see IDOR / 2FA skip / bad webhook, POST those reasons. Do not invent them in YAML.

Live filters: severity row, then Everything / Web / Linux / App login / Tenants / Probes. That is how SSH and app-login rows stop burying a SQLi.
