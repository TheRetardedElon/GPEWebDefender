Access-log ceiling

VisibleInvisible
Method, path, query string, status, UA, referer, client IP, bytes POST / PUT bodies
GET-based SQLi, XSS, traversal, exploit-path hunting SQLi or XSS that exists only in a JSON body
Scanner user-agents, 404 storms, login POSTs to known paths Authenticated abuse that looks like normal traffic
What nginx logged What nginx never saw (direct-to-app bypass, non-HTTP)
Do not “fix” this by logging bodies Access logs with $request_body will eventually contain passwords, tokens, or card data. If you need POST visibility, ingest a dedicated app/WAF audit stream that is already redacted — later.

False positives (known)

RuleTypical FPMitigation
web.xss.script Asset URLs that look like markup not_pattern skips common static extensions
web.recon.backup Real downloads named .zip / .sql Expect some noise; filter the UI or tighten the pattern
web.scan.404storm A broken crawler or a bad deploy that 404s everything Raise count if your site is noisy
web.brute.login A legit app that POSTs /api/auth a lot (token refresh) Narrow path_contains to the real login path
web.scanner.ua A security team running nuclei against themselves That is a true positive from the monitor’s point of view

Resource contract

PieceTarget
Manager + SQLite, small siteComfortable on 1 GB RAM. No JVM.
AgentTiny — tail + HTTP client
CPUIdle near nothing; regex per line is cheap at typical web QPS
DiskSQLite + WAL. Event prune default 7 days; alerts kept 4× that

If you need billions of rows of search, do not add OpenSearch. Next store is a purpose-built log engine (VictoriaLogs class), not a Java indexer. See 12.

What we will not add “just because”

  • OpenSearch / Elasticsearch / Graylog as a dependency.
  • A JVM for any reason.
  • Logging request bodies that might contain secrets or card data.
  • A public UI with no gate on a product host.
  • Pretending this is a WAF or a full SOC.
